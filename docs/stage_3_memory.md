# AutonomOS — Stage 3 Persistent Project Memory Specification & Documentation

## 1. Executive Summary & Core Philosophy

Stage 3 establishes the **Persistent Project Memory** subsystem for AutonomOS. It provides an externalized, human-readable, versionable, and deterministic repository knowledge base stored in Markdown files under `.autonomos/` and indexed in SQLite.

```
┌────────────────────────────────────────────────────────┐
│                      Repository                        │
│            (Source of Truth for Code)                  │
└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐
│              Persistent Project Memory                 │
│         (Structured Understanding in Markdown)         │
│  .autonomos/memory/, decisions/, tasks/, reports/      │
└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐
│                    Context Engine                      │
│             (Stage 4 — Context Selection)              │
│       Selects what information enters AI context       │
└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐
│                      LLM Context                       │
│    (Ephemeral context window for active reasoning)     │
└────────────────────────────────────────────────────────┘
```

### Core Memory Invariants
1. **Context is NOT permanent memory**: LLM context windows are ephemeral and limited. Persistent project memory externalizes architectural invariants, past decisions, task summaries, and reports so they survive beyond individual worker executions.
2. **Deterministic & Inspectable**: Memory is stored primarily in standard Markdown files that humans can inspect, edit, and version-control via Git.
3. **Strict Source-of-Truth Hierarchy**:
   - **Task runtime state** $\rightarrow$ SQLite Task Engine is authoritative.
   - **Project implementation** $\rightarrow$ Git repository code is authoritative.
   - **Historical facts** $\rightarrow$ Append-Only Event Store is authoritative.
   - **Project memory** $\rightarrow$ Managed Markdown in `.autonomos/`. Updating a markdown file cannot bypass or alter runtime state.
4. **Separation of Knowledge vs. Context Injection**: Stage 3 answers *"What does the project know?"*. Stage 4 (Context Engine) will answer *"What does this worker need to know right now?"*.

## 2. Persistent Memory Hierarchy & Layout

When a project is created, AutonomOS manages the following directory structure inside the project root:

```
<project_root>/
├── .autonomos/
│   ├── memory/
│   │   ├── project-map.md       # High-level component and navigation map
│   │   ├── architecture.md      # Stable invariants, component boundaries & constraints
│   │   └── current-state.md     # Active stage, completed milestones, active work, limitations
│   ├── decisions/
│   │   ├── 0001-use-sqlite-wal.md
│   │   └── 0002-jwt-token-auth.md
│   ├── tasks/
│   │   ├── task-001.md          # Human-readable task knowledge, findings & outcomes
│   │   └── task-002.md
│   ├── reports/
│   │   ├── task-001/
│   │   │   └── execution.md     # Worker-generated execution & verification reports
│   │   └── task-002/
│   │       └── research.md

│   │   └── issue-4f9a12c8.md    # Structured known problems and severity
```

## 3. Managed Memory Types (`MemoryType`)

| Memory Type | Path Pattern | Purpose |
| :--- | :--- | :--- |
| `PROJECT_MAP` | `.autonomos/memory/project-map.md` | Concise navigational overview of components and directory locations. |
| `ARCHITECTURE` | `.autonomos/memory/architecture.md` | Stable architectural decisions, constraints, and integration boundaries. |
| `CURRENT_STATE` | `.autonomos/memory/current-state.md` | Current milestone, completed capabilities, active work, and known issues. |
| `DECISION` | `.autonomos/decisions/XXXX-<slug>.md`| Architecture Decision Records (ADRs) with Context, Decision, Reasoning, and Consequences. |
| `TASK_MEMORY` | `.autonomos/tasks/<task_id>.md` | Human-readable task objectives, relevant repository files, findings, and outcome. |
| `REPORT` | `.autonomos/reports/<task_id>/<type>.md` | Execution and verification reports generated by workers. |
| `ISSUE` | `.autonomos/issues/<issue_id>.md` | Lightweight tracking of known problems, severity, and affected areas. |
| `NOTE` | `.autonomos/notes/<name>.md` | General project notes. |

## 4. Memory API & Methods

`MemoryManager` (accessible via `runtime.memory`) provides a deterministic programmatic API:

```python
# Create custom memory document
doc = runtime.memory.create_memory(
    project_id="proj-1",
    memory_type=MemoryType.NOTE,
    title="Performance Tuning",
    content="# Performance Tuning\nUse WAL mode.",
    relative_path=".autonomos/notes/perf.md",
    references=["core/storage/sqlite_store.py"]
)

# Record an Architectural Decision (ADR)
adr = runtime.record_decision(
    project_id="proj-1",
    title="Event Sourced Runtime",
    context="We need full auditability.",
    decision="Record all runtime actions as immutable events.",
    reasoning="Enables timeline replay and UI streaming.",
    consequences="Requires sequence indexing.",
    decision_number=1
)

# Update current project state
runtime.update_current_state(
    project_id="proj-1",
    stage="Stage 3 Complete",
    completed_milestones=["Core Runtime", "Event System", "Project Memory"],
    active_work=["Tool Runtime"],
    known_limitations=["Context Engine pending Stage 4"]
)

# Audit project memory for stale or broken references
audit_reports = runtime.audit_project_memory("proj-1")
for report in audit_reports:
    if not report.is_valid:
        print(f"Stale references in {report.relative_path}: {report.broken_file_references}")
```

## 5. Atomicity, Safety & Concurrency

1. **Atomic Disk Synchronization**: All file writes are performed via `NamedTemporaryFile` in the same directory followed by `os.replace` to prevent partial writes or file corruption during power failures or concurrent operations.
2. **Optimistic Versioning**: `MemoryDocument.version` increments on every update. Passing `expected_version` ensures concurrent modifications do not overwrite newer versions silently (raising `MemoryConflictError`).
3. **SHA-256 Checksums**: Every document computes `checksum = sha256(content)` to verify file integrity on disk and during database reloads.

---

## 6. Stale Memory & Reference Validation

The `validate_memory_references` and `audit_project_memory` functions inspect all references within managed memory:
- Validates that repository file paths (e.g. `core/storage/sqlite_store.py`) exist on disk.
- Validates that referenced `task_id` values exist in the Task Engine.
- Validates that referenced `worker_id` values exist in the Worker Registry.
- Flags broken references with structured `ValidationReport` instances.

## 7. Event & Activity System Integration

All memory operations emit typed Stage 2 events:
- `MEMORY_CREATED`
- `MEMORY_UPDATED`
- `MEMORY_DELETED`
- `DECISION_CREATED`
- `REPORT_CREATED`
- `ISSUE_RECORDED`
- `ISSUE_UPDATED`

These events are automatically projected into UI activity items with dedicated icons and levels.
